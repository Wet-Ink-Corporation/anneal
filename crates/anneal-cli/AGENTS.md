# Crate charter: `anneal-cli`

## Purpose
The `anneal` binary: the deterministic layer behind the plugin's hooks and skills. It is the composition root, so argument parsing, output formatting and exit codes live here. Domain logic moves into library crates when a second consumer appears (ARC-07).

## Layer
binary. Owns process concerns: arguments, stdout and stderr, exit codes. The code lives in an internal library target (`anneal_cli`, `src/lib.rs`) so tests and doctests can reach it; `src/main.rs` only passes the process's arguments and streams to `cli::run`.

## Allowed dependencies
- Workspace crates: `anneal-ledger` (event registry and store).
- Third-party: `clap` (derive; command tree and help), `serde` and `serde_json` (envelope, snapshots), `thiserror` (error enums), `sha2` (content hashes for the lint snapshot), `ureq` (3, `rustls` only: Clef's HTTP transport); dev: `tempfile`. Each addition is an H-16 decision recorded below.
- Never: anything that needs a network at build time.

## Public surface
The contract is the command line, the JSON envelope on stdout and the exit codes in `docs/exit-codes.md`. The `anneal_cli` library is internal (`publish = false`) and not a stable API.

## Invariants
- `--help` and `--version` exit 0 (only as the last argument); a usage error exits 2 and writes nothing on stdout.
- Every error is exactly one `ERROR <reason>` line on stderr, and nothing on stdout.
- No failure exits 0; the envelope's `ok` is true exactly when the exit code is 0. The one exception is `anneal hook <name>`, which fails open: it notes its failures in its output (or in one `ERROR` line on stderr when stdout cannot be written) and exits 0; only its usage errors exit 2 (`a_closed_stdout_still_exits_0_with_one_error_line`). A guard (`hook guard`, or a hook passed `--fail-closed`) fails closed instead: it denies what it cannot judge (bad or oversized input, an unparseable command) with a deny decision on stdout and exit 0, and exits 2 with one `ERROR` line when that decision cannot be written (`a_closed_stdout_exits_2_with_one_error_line`).
- The guard is silent when it allows; a denial is one `PreToolUse` deny decision whose reason is one `ERROR` line, plus a `gate_blocked` event, and a ledger failure never turns a deny into an allow (`tests/it/hook_guard.rs`, `hook::guard::tests`). The denylist never allows: it denies or leaves a command to `guard::Fallback`.
- Clef D1 in the guard is asked only for a Bash command the denylist did not deny, never changes the verdict outside enforce mode (off, misconfigured, shadow, or `enforce` in its first 50 answered decisions), and never turns a Clef failure into a deny: in enforce mode a `deny` action denies (`guard.destructive`), an `ask` action or no answer with the `ask` fallback asks, anything else allows. When D1 is configured to enforce, a failure to run it asks, and an answer that cannot be logged keeps its deny or ask (a defer asks): a failure never becomes an allow there. A deny records in the time left of the 4.5 s budget measured from the hook's start, or skips the record with a note. The command Clef gets and the row keeps is trimmed, cut to 1,024 characters and redacted wherever the text appears (env-like and credential-named assignment values, quoted names included, the value after any credential-named key in a word, the values of credential-named options with one dash or two (not `-stdin`, `-file` or `-env` ones) and of credential-named configuration keys (`user.password x`), credential-named header values to the end of their simple command (never past a separator; in a quote or substitution the plain `name=value` pairs after a `;` too, a pair being a word with no `$`, backtick, `\` or `(` whose value holds no blank or `;` and closes any quote it opens), a value attached to a header-shaped name (`Cookie`, or a hyphenated name ending in a credential word: `Cookie:a=1`, `X-Api-Key:k`, `db-password:/p`) hiding only its own word, with the pairs after it only when a `;` ends it, the word after `vault login`, the word after `Bearer` or `Basic`, URL userinfo, obvious tokens, the secret options of known tools, comments, heredoc bodies, and everything after an unclosed span); a row's `input` is at most 2 KiB of JSON and absent for rows asked without one (`hook::guard::clef::tests`, `hook::guard::redact::tests`, `decide::client::tests`, `tests/it/hook_guard_d1.rs`).
- A `hooks.json` entry sets `onFailure: "block"` exactly when it passes `--fail-closed` (`an_entry_blocks_on_failure_exactly_when_it_passes_fail_closed`).
- The preconditions hook judges an edit by the edited file's own worktree, found from the file's longest existing ancestor directory, never from the hook's cwd. It is silent for a file in no git repository, with no ledger file for its repository (and never creates one), and with no `mode_set` (or `off`) for its worktree; in a mode it always allows test files (floor-guard's, plus `tests.rs`/`test.rs`), the build's plan and tree, `.temper/`, `.anneal/`, `tmp/`, `scratch/` and prose documents, and denies any other edit until the mode's preconditions hold (build: spec lints clean, tree confirmed at its current hash, clean at entry, plan approved and current; diagnose: a `repro_red` tagged with the worktree key after the latest `mode_set`). The plan's `Spec:` line exempts nothing. Unreadable input, and a ledger, git or path it cannot read once a ledger exists, deny; a deny is one `ERROR` line naming the missing precondition and its command, plus `gate_blocked` (`tests/it/preconditions.rs`, `mode::scope::tests`).
- The completeness (Stop) hook never blocks a stop with `stop_hook_active`, outside a git repository, or more than twice in a row for a session without a tool call in its transcript since the last block; it blocks only on a hard gate (a success claim while a source file changed after the worktree's latest believable green `test_run` started, or a `[DEBUG-<id>]` leftover), names the command that clears it, and records a `stop_blocked` (`completeness.<gate>`) in an existing ledger; playbook gaps are only `additionalContext`. Anything it cannot check is one `ERROR` line as the `systemMessage`, never a block on its own; it never creates a ledger (`tests/it/hook_completeness.rs`).
- The status (SubagentStop) hook never blocks and never creates a ledger; with a ledger it appends exactly one `subagent_status` per stop, a missing or malformed status block being its `violation` rather than a failure (`tests/it/hook_status.rs`, `hook::status::block::tests`).
- The route and ruled-before (UserPromptSubmit) hooks always exit 0 (only usage errors exit 2); with Clef off they read, write and create nothing; they inject at most one line of `additionalContext` each, only when the point's effective mode is `enforce` and its rule gives `hint` (route, and only for a phase with an entry skill) or `surface` (ruled-before, and only for a ruling, never `none`); an unanswered call is silent; an answer whose row was not logged is never acted on; Clef is asked only while its 2 s timeout fits in the 4.5 s budget measured from the hook's start; their other failures (a log failure and a spent budget among them) are one `ERROR` line as `systemMessage`; the prompt sent to Clef is redacted and at most 1,024 characters, and no row keeps it; ruled-before offers at most 31 rulings plus `none`; a route decision is labelled at most once (`hook::route::tests`, `hook::ruled_before::tests`, `hook::prompt::tests`, `decide::redact::tests`, `tests/it/hook_prompt.rs`).
- `mode` appends exactly one `mode_set` per run to the ledger the hook reads (no `--store`), with the envelope `worktree` set to the worktree key (`mode::scope::worktree_key`), and `plan` and `tree` relative to the worktree root; a dirty tree is recorded (`clean: false`, a `mode/dirty` finding, exit 0); a `--plan` or `--tree` that is not a file inside the worktree, or a `--store`, is a usage error and records nothing (`tests/it/preconditions.rs`).
- Every exit code is declared in `exit_codes`; `docs/exit-codes.md` is generated from it and a test fails on drift.
- Every `hooks.json` entry is exec form (`${CLAUDE_PLUGIN_ROOT}/libexec/anneal` plus `args`) with `onFailure` and an explicit `timeout`, runs an `anneal hook` subcommand the binary accepts, and has exactly one row in `hooks.metadata.json` (and every row an entry); the metadata validates against a strict DTO that agrees with `hooks.metadata.schema.json` (`tests/it/hooks_manifest.rs`).
- `dag` output is in `TicketId` order (numeric ids by value first, then bytes) and byte-identical across runs; a dangling reference exits 2 even when there is also a cycle (exit 1 otherwise); the frontier of a graph that fails the check lists nothing; cycle detection is iterative; external tickets (outside blockers a tracker resolves) are leaves, never counted or ready; every tracker is read-only and bounded, and fails rather than truncates (`tests/it/dag.rs`, `dag::graph::tests`). The GitHub reader is tested only through `GhApi` against recorded JSON, never the network.
- A design tree is read up to 1 MiB, 512 nodes, 256 turns and 64 dependencies per node, and its version is read before the strict parse; one with a `depends_on` cycle, a dangling or repeated dependency, a duplicate or bad id, a blank text or a probability outside 0..=1 is invalid (exit 1, one finding per problem), and its frontier is exactly the open nodes whose dependencies are all answered, by id (`grill::tree::tests`, `the_schema_*_agree_with_the_design_tree_dto`).
- `grill classify` asks Clef D7 only about an `open` node of a valid tree (an invalid tree exits 1, a missing or settled node is a usage error; nothing asked either way); with Clef off it asks, logs and writes nothing; it changes the tree file only when D7 is in effect `enforce` (not while a configured `enforce` is in its first 50 answers) and the answer's row was logged, and then only that node's `is_decision`, nodes kept in file order, at the resolved path so a symlinked tree stays a link; in shadow, unanswered or misconfigured (including thresholds or an anneal home that cannot be read) it leaves the file byte for byte and exits 0; an answer it cannot log exits 70; the row keeps neither question nor goal (`grill::classify::tests`). One session's D1, D3, D6 and D7 rows are all read by `calibrate` (`release_check`, `tests/it/release_check.rs`).
- `grill confirm` appends exactly one `grill_confirmed`, carrying the tree's `sha256:` hash and the human's words, and only with a non-blank `--quote`, a `--tree` and `--session` the ledger accepts as tags, a valid tree and no open node; otherwise it appends nothing and opens no ledger (`tests/it/grill.rs`).
- The bootstrap index is 200 words or fewer, lists `ENTRY_SKILLS` in order, and passes `anneal lint skills --index docs/bootstrap-index.md`; live state comes after it, only when it changed for the session, and the bootstrap never creates a ledger (`tests/it/hook_bootstrap.rs`).
- `lint terms` reports a term only with a non-word character (word: Unicode alphanumeric or `_`) or the line edge on each side, in any letter case, at most once per file, line and term; `_Avoid_:` lines are never hits; a file over the read cap is listed under `skipped`, never dropped (`lint::terms::tests`, `tests/it/lint_terms.rs`).
- `lint spec` exits 1 exactly when `data.findings` is non-empty, always reports `data.needs_clarification` (markers outside code fences, comments and inline code), parses EARS keywords only in capitals, and lints the shipped `spec.template.md` clean (`lint::spec::tests`, `tests/it/lint_spec.rs`).
- `lint plan` exits 1 exactly when `data.findings` is non-empty, and the shipped `plan.template.md` checks clean; `data.plan` agrees with `plan.schema.json` (`lint::plan::tests`, `tests/it/lint_plan.rs`).
- `plan approve` appends at most one `plan_approved`, and none, opening no ledger, while `lint plan` has a finding or the linked spec has any `[NEEDS CLARIFICATION]` marker; approving content already approved appends nothing. `plan check` exits 0 only when the latest approval of the plan id has the `sha256:` hash of the plan's current bytes, 3 with no approval, 4 otherwise, and never creates a ledger (`tests/it/plan.rs`).
- `task done` appends `task_done` only after its test command exited 0, always after that run's `test_run`; a non-zero exit, a signal or the timeout appends only a red `test_run` (exit 1); a command that cannot start, a non-UTF-8 command, or a task id or `--session` the ledger cannot tag appends nothing and opens no ledger (exit 2); the ledger is opened only after the command finishes. The test command's own output is the one thing `anneal` passes through to stderr besides an `ERROR` line (`tests/it/task.rs`, `task::tests`); the only other non-error stderr is `calibrate`'s summary, written after its envelope.
- `repro record` appends exactly one `repro_red` (`task` the `--id`, default `repro`; `test` the command; envelope `worktree` the worktree key) only when its command exited non-zero or was killed by a signal, and exits 0 then; a command that exits 0 (3), runs past `--timeout` (4) or cannot start (2) appends nothing and opens no ledger; outside a worktree, or with an id or `--session` the ledger cannot tag, it is a usage error that runs nothing; it has no `--store` (`tests/it/repro.rs`, `repro::tests`, `tests/it/preconditions.rs`).
- `repro leftovers` and `repro::debug_leftovers` read only the files `git ls-files --cached --others --exclude-standard` lists (by raw name on unix; elsewhere a name that is not UTF-8 goes to `skipped`), as bytes, each up to 1 MiB and 64 MiB in all (a file over either in `skipped`, the total also setting `over_budget`), report at most 1,000 `{file, line}` by file then line (the rest in `omitted`), and count a tag only as `[DEBUG-` + 1 to 64 of `[A-Za-z0-9_-]` + `]`, so a placeholder such as `[DEBUG-<id>]` is not one; exit 1 exactly when a tag is found (`repro::leftovers::tests`, `tests/it/repro.rs`).
- `floor-guard` exits 0 only when it read the whole diff and found nothing, 1 exactly when `data.findings` (or `data.omitted`) is non-empty, and 2 with one `ERROR` line and nothing on stdout when it could not read it all (no repository, an unresolvable base, a git failure or timeout, output over 16 MiB); detections look only at added and removed lines (`tests/it/floor_guard.rs`, `floor_guard::detect::tests`, `floor_guard::diff::tests`).
- `decide` asks Clef only for a question the point's thresholds define, with valid options; with a malformed account, token or mode it exits 5 with the point's fallback and `data.reason`, calls nothing and logs nothing; with mode `off` or no account it exits 3 (reporting `configured_mode`), calls nothing and logs nothing; otherwise it appends exactly one row per call (answered: exit 0; unanswered: exit 5 with the point's fallback, `unreachable` true for unreachable and timed out), applies the bands to the probability (noul `yes`, choice top option, score value), never to `confidence`, and reports `enforce` only after 50 answered decisions of the point, counting only questions whose rule has bands (a record-only answer, such as D3's size, never advances it: `an_answer_to_a_bandless_question_is_logged_but_does_not_advance_the_shadow_period`). The token is in no row, envelope, error or `Debug` output; the log is under the anneal home, never the plugin's directories; rows are at most 8 KiB and the log at most 5 files of 16 MiB (`decide::client::tests`, `decide::tests`, `tests/it/decide.rs`).
- `calibrate` reads every decision log file (oldest first, each a regular file of at most 16 MiB plus 64 rows of 8 KiB), takes the last label of each id, and never writes the thresholds file or the mode: its only write is `<anneal home>/decisions/proposals.json`, holding all seven points whatever `--point` selects. A question with fewer than 50 labelled decisions, a Brier score over 0.15 or an ask rate of 20% or more is `stay-shadow`; a point is `eligible-to-enforce` only when it has decisions on a question whose rule has bands and every such question with decisions is; a bandless (record-only) question such as D3's size never holds a point back (`unlabelled_rows_of_a_bandless_question_do_not_hold_a_passing_point_back`). A proposed threshold stays strictly below the next band up and is a change only when it costs strictly less than the current one on the labelled set; otherwise the current value is reported and no apply step is listed. A line it cannot read is counted, never fatal; the envelope (exit 0) comes before the stderr summary, which is best effort: a stderr that refuses it leaves the exit code 0 (`calibrate::score::tests`, `calibrate::report::tests`, `calibrate::read::tests`, `calibrate::tests`, `tests/it/calibrate.rs`, worked through in `tests/fixtures/calibrate/README.md`).
- ADR numbering is a pure function of the directory's file names and the title: the same inputs give the same `Placement`, a recorded title gets its existing ADR back, and numbers are never reused (`adr::tests`).
- `verdict set` appends exactly one `verdict_set` carrying the resolved full commit, the base and the patch id of `git diff <base>...<sha>`, to the ledger the hook reads (no `--store`); a commit or base that does not resolve, or a `--pr` or `--session` the ledger cannot tag, is a usage error that opens no ledger. `verdict valid` exits 0 when the latest fresh verdict is a level, 3 when it is `noise_only`, 1 otherwise, and never creates a ledger; a verdict is fresh only for its own commit or for the same patch id from the same base (`tests/it/verdict.rs`, `verdict::assess::tests`).

## Errors
Usage errors exit 2 (as do `task done` and `repro record` when their command cannot be started and every `floor-guard` tool error, each with its own row in the command's table; `decide`'s refused state, question, options or label are usage errors too), stubs 64, internal errors (git, snapshots, the ledger store, a tracker that cannot be read, `decide`'s thresholds file, log or clock, `calibrate`'s log, thresholds or proposals file) 70, a target `watch` cannot read (gh failing, a missing pull request, commit or deployment, an answer it cannot decode, a closed pull request, too many items) 7 (`WatchError`, `exit_codes::WATCH_QUERY`), and a write failure on stdout or stderr 74. A command's own outcomes (cycle, red test, findings) are envelopes with per-command codes, not errors.

## Test strategy
Unit tests beside the code for parsing and output; integration tests in `tests/it/` run the built binary. Run with `cargo test -p anneal-cli`. `tests/it/repo_gates.rs` runs the repository's own `plugin/skills` and `evals/routing` against the Tier 0 and Tier 1 bars, so CI's `cargo test` enforces them. `tests/it/dry_run.rs` replays the recorded define chain in `evals/fixtures/dry-run/` (grill, spec, plan, tickets) on a temporary copy and compares the ledger events with its `events.jsonl`; a change that alters an artifact or an event re-records the fixture (its README says how).

## Do not
- Do not print with `println!`; write through a locked handle.
- Do not open the ledger anywhere but through `anneal_ledger::Store`, and do not resolve its path anywhere but `paths::ledger_store` (or `paths::ledger_store_within`, its variant with a caller's git timeout).
